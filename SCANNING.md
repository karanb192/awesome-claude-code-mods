# How discovery and validation work

The catalogue lists discovered plugins whose `hooks/hooks.json` names a module, excluding test fixtures, mirrors of Anthropic's own mods and copies inside a catalogue. Repos in `data/catalogs.txt` are named once with their count, so their stars never rank a copy above the author's own repo. A mod its author has moved to another repo counts once, on the copy named in `data/duplicates.txt`; the scanner flags same-owner same-name pairs for review and never collapses them on its own. Entries are sorted by hosting repository stars, which do not measure installs or popularity of an individual mod.

Reach is the widest thing the mod's `$` calls can touch. L0 draws and remembers, L1 reads, L2 writes files, runs processes or drives Claude, and L3 reaches the network. It is a footprint, not a verdict; a PR tracker has to run `gh`. Sees lists what the mod observes without a matcher.

Discovery searches GitHub code for `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS` and for a `hooks/hooks.json` with a `modules` key, and adds the repos in `data/seeds.txt`. Repository search adds repositories pushed since the last complete search that have a mod topic or "claude mod" in the name or description, and keeps one only when its file tree has a `hooks/hooks.json` that lists modules. Each query covers its time window in slices small enough for one page of results, so no slice reaches GitHub's 1,000-result cap. Progress is in `data/discovery.json`, which records when the last complete search started, the repositories already found not to be mods, those left for the next run and those found but not yet merged. Scheduled runs pass it to the next run through the Actions cache, so progress does not wait for a merge. Code search runs once a day. Scans every three hours and after a seed is merged use the known candidates, the seeds and repository search. The scanner clones each repo shallow, finds every plugin with a hooks module, and runs `claude plugin validate` on its `plugin.json`. The validator inventories the source and prints the events hooked and the `$` calls made; no mod code runs. The grader turns the calls into a reach level and the hooks into a visibility list; its rules are in `tools/grade.mjs` and tested. The renderer writes this catalogue, the README count, one badge pair per mod under `badges/`, and the searchable collection under `docs/`, which GitHub Pages serves as mods.aidojo.si.

Discovery retains previously found repos and splits searches above GitHub's 1,000-result limit by file size. Incomplete responses are retried; missing pages or changing counts trigger smaller searches. A partition that remains capped or incomplete fails the code search instead of publishing partial results. Each partition must be complete, but GitHub does not provide an atomic snapshot across searches. This covers the configured searches, not every repository on GitHub: indexing and search-pattern limits still apply.

Search requests run sequentially with a ten-second pause. Rate-limit retries honor GitHub's cooldown and quota-reset headers and use exponential backoff with jitter. Each request gets at most seven attempts, with a shared 30-minute retry-wait budget across both searches. If the required wait exceeds the budget, or the code search fails another way, the daily scan discards that search, keeps the known candidates and seeds, and says so in the scan pull request. Discovery never removes a candidate. Logs include rate-limit headers and request IDs for diagnosis.

Scheduled scans retain missing plugins with their last known footprint and mark them “not verified”. A separate weekly retirement workflow proposes removals only when a fresh, successfully inspected checkout no longer contains the hook module. Failed clones, malformed hook files and validation failures do not justify removal. The proposal records the checked revisions in `data/retirements.json` and requires a maintainer merge. Exception seeds remain candidates until reviewed separately; curated descriptions are maintained by hand.

Pull-request checks combine committed candidates with submitted seeds without running global discovery. Newly added seeds must clone successfully and contain mod plugins that pass validation, with warnings allowed.

Validation is a static check, not a runtime compatibility test. Reserved plugin names fail validation; the raw data and each website entry’s “Access & validation details” section retain the reason. The scanner also validates ancestor marketplaces that list the plugin through a local source path. A marketplace failure appears separately because loading the plugin directly is a different install route. Incomplete or unrecognized results stay “not verified”.

“Review UI rewrite” means that a mod hooks `ui.render` and its module source or local imports contain control-character strings. The scanner parses JavaScript and TypeScript without executing them, and links each finding to the scanned commit. It excludes comments, regular expressions, tab and newline characters. This is a source-review warning: the strings can have other uses, and computed strings, external packages or unresolved imports can escape detection. No warning does not prove runtime compatibility. See the [2.1.287 compatibility report](https://github.com/karanb192/awesome-claude-code-mods/issues/21) for the reported restriction on rewritten text.

Benchmark directories and plugins that identify themselves as fixtures or non-installable harnesses are recorded but excluded from the mod count, tables and badges. Confirmed course exercise folders are also excluded; finished mods in the same repository still count. Confirmed local copies use individual duplicate mappings so original mods in a mixed repository remain listed. The workflow tests classification and renders sample lists of up to 1000 mods in Chromium at desktop and mobile widths before scanning.

The [raw scan result](https://mods.aidojo.si/mods.json) records each entry. See [Contributing](contributing.md#running-the-tools) to reproduce the scan or add badges to your own mod.
